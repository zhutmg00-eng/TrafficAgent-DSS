# TrafficAgent-DSS 审查报告 / Review Findings

日期: 2026-09-12 · 审查对象: `zhutmg00-eng/TrafficAgent-DSS` (ITSAC 2026 参赛工程)
审查方式: 源码走查 + 实际运行（无 SUMO 环境下逐个接口/模块实测）

---

## 0. 结论速览

工程整体是一个**结构完整、注释详尽的"演示级"决策支持系统**：FastAPI + 原生 JS 前端，
Webster/绿波/动态分流三个交通工程工具都真实实现了算法，且代码里保留了多次"修复踩坑记录"
（如流量排序、`setPhaseDuration` 破坏感应控制、`getArrivedNumber` 累积等），说明作者迭代认真。

但它在**"真实感"和"可用性"上有系统性缺口**——恰好就是用户提出的 4 个问题。根因可以概括为：

> 系统把**数值算得很精致**，却把**场景做得很假、把结论讲得很虚**。

---

## 1. 用户已提出的 4 个问题（确认 + 定位证据）

### 问题①：没有真实路网图 / 可视化不直观 / 路网数据缺失  —— 确认（最严重）

证据：
- `scenarios/corridor.{nod,edg}.xml` 仅描述**一个三路口走廊**：`J1/J2/J3` 三个信控口 +
  一条北侧绕行支路 + 三条支路，节点坐标是手写的 `x=-800..600`。**这不是真实路网**。
- `README.md` / 技术方案宣称"基于 OSM 真实路网（西直门/中关村）"，但**仓库内没有任何 OSM 数据、
  没有 netconvert 的 OSM 导入流程**，"真实路网"名不副实。
- 前端 `src/web/static/js/dashboard.js` + `index.html`：**完全没有地图/路网渲染**。
  "态势感知"只是 4 张 KPI 数字卡；没有路网拓扑、没有逐路段热力、没有拥堵空间分布。
- 场景下拉里的 `corridor_2nd_ring` 等选项与 `west_arterial` **共用同一套 SUMO 网络**，
  只是改了标题文案——切换场景视觉上没有任何路网变化。

### 问题②：方案/话语"不明所以"，看完仍不知道要做什么 —— 确认

证据：
- `_diagnose_deterministic()` 产出的思维链大量使用内部黑话：`空域分流 / 时域扩容 / 激波回传 /
  绿信比自适应再分配`，缺少"这意味着现在该干什么"。
- `generate_decision_report()` 的"三、决策推荐与协同处置指令建议"是**散文式**描述，
  没有"谁、在什么位置、按什么参数、什么时候执行、如何验证"的可执行结构。
- 前端"策略卡片"只给名称与少量参数，**没有行动清单**，也没有"预期效果 / 责任方 / 验证指标"。

### 问题③：前端"AI 味"太重 —— 确认（用户后续提供 UI 资源再改造）

证据：深色渐变 + 等宽字体 + emoji 堆叠 + "终端窗口"式 CoT 流式打字机。属于审美问题，
需等用户提供设计资源。本轮**仅做结构/信息层改进，不做视觉大改**。

### 问题④：路况数据采集太少 / 数据不足 —— 确认（与①同源）

证据：
- 默认推演走 `get_calibrated_rollout_data()`：**大量核心指标是硬编码常量**
  （如延误基准值、队列时间序列由公式生成），并非仿真产出，且**换场景数值基本不变**。
- `/api/evaluate/multi-seed` 的"蒙特卡洛"只是给同一组常量加 `±2%` 噪声，
  得到的"置信区间/显著性"**统计上无意义**。
- SUMO 沙盒只采集**单一瓶颈边**的排队/速度，加全网 CO2/油耗，**没有逐路段、逐车道、
  分流向的检测器数据**，支撑不了"路网级"治理展示。

## 3. 本轮已实施的修复（本地，未上传）

> 目标：在**不引入重型依赖**、**不依赖 SUMO/联网** 的前提下，真实解决①②④，并为③留好结构。

### Fix-1 · 真实路网（对应①，并补④的数据底座）
- 新增 `scripts/build_network_from_osm.py`：把 Overpass 的 OSM 几何导出编译为自包含路网 JSON
  （在路口处切分路段、投影为局部米制坐标、解析 `lanes/maxspeed/oneway/name`）。
- 已实测抓取并生成 **西直门枢纽真实路网**：`scenarios/network_xizhimen.json`
  —— **591 节点 / 771 路段 / 143.2 km / 92 个信控候选路口**，含真实路名
  （西直门外大街、北二环、德胜门西大街、学院南路…）。
- 新增 `src/data/network.py`：路网数据模型（拓扑、几何、邻接、瓶颈选取）。

### Fix-2 · 路网级中观仿真引擎（对应④，且让①有真数据可画）
- 新增 `src/simulation/mesoscopic.py`：**确定性**链接级排队模型（外生需求 + HCM/Webster
  延误 + Little 定律排队 + 事故降容 + 绿波/分流控制效应），**无需 SUMO 即可运行**，
  输出**逐路段** `speed/queue/flow/occupancy/delay` 时间序列。
- 实测（西直门路网，事故 150–420s）：baseline→策略B：延误 −87%、排队 −71%、
  速度 +68%、瓶颈放行 +16%、CO2 −33%；且 baseline→A→B **单调改善**，符合工程直觉。

### Fix-3 · 后端 API（对应①④）
- 新增 `src/web/network_api.py`：`GET /api/network`（路网拓扑 + 实时拥堵着色）、
  `GET /api/detectors`（逐路段检测器明细）、`POST /api/action-plan`（行动清单）。
- `/api/rollout` 改为：**优先真实路网中观推演**，SUMO 可用时仍走微观沙盒，
  仅当数据层也缺失才回落到标定常量；响应新增 `engine / network / map_snapshot / detectors`，
  明确标注数据来源（修补 E1/E2 的"假装仿真"）。

### Fix-4 · 可执行行动清单（对应②）
- Agent 侧新增 `formulate_action_plan()`：输出**大白话总述 + 5–7 条按紧急度排序的行动**
  （动作/位置/时机/预期效果/责任方/验证方式），数值全部取自已算出的方案参数；
  决策简报新增"行动指令清单"章节，替换原有虚化表述。

### Fix-5 · 前端（对应①②④，结构层）
- 新增三大区块：**真实路网数字孪生地图**（SVG 绘制，按拥堵等级着色、瓶颈脉冲高亮、
  悬停/点击详情、方案切换）、**行动指令清单**、**路网检测器数据表**。
- 未做视觉大改，等用户 UI 资源（对应③）。

## 4. 仍未解决 / 建议后续

- ③ 视觉改造：等设计资源；当前已把"信息结构"理顺，便于套皮。
- OSM→SUMO 的 netconvert 流程本环境缺 SUMO，未落库；若赛题要求 SUMO 物理仿真，
  建议在比赛机安装 SUMO 后用同一 `network_xizhimen.json` 走 `netconvert --osm-files` 生成 `.net.xml`。
- 多场景（不同路口）可复用 `build_network_from_osm.py` 指到其它 bbox 即可。
- 蒙特卡洛应在**真实随机源**（SUMO seed / 需求扰动）上进行，而非给常量加噪声。
